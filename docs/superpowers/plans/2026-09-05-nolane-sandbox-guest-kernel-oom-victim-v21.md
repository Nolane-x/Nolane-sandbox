# Wave 21 Implementation Plan — Guest Kernel OOM Victim Provenance

## Goal

Implement the approved Wave 21 design as an additive, fail-closed evidence plane that can prove that the guest Linux kernel marked an exact process lifetime belonging to an exact sandbox realization as an OOM victim. Preserve all existing workload execution and `GetOOMEvent`/`TaskOOM` compatibility behavior. Never infer `OOMKilled`, causal termination, or main-process victimhood from weaker signals.

- Base: Wave 20 final head `66624d215af57cf342fba4f10c7282818f45868a`.
- Head branch: `gpt/wave21-guest-kernel-oom-victim-provenance`.

## Non-negotiable truth boundary

Wave 21 may claim only that the guest kernel marked an exact guest process lifetime as an OOM victim and, when separately provable, that the victim was the realization's exact MAIN process or an exact MEMBER process.

Wave 21 must never synthesize proof from any of the following by themselves: `TaskOOM`, existing `GetOOMEvent`, `memory.events`, exit 137, SIGKILL, Wave 18 cgroup OOM delta, Wave 19 host identity, Wave 20 host victim proof, PID-only equality, an old realization token, or missing evidence.

Evidence/capability failures are observational only. They do not fail container Start/Wait/State or sandbox execution.

## Data-flow authority

```text
Wave17 generation authority (Cubelet)
  -> 256-bit CSPRNG realization token
  -> one-shot/poisonable CubeShim token slot before main Start
  -> exact guest StartContainer token
  -> guest-local realization window + exact guest main identity
  -> guest oom:mark_victim collector
  -> immutable finalized exact-token evidence at guest WaitProcess
  -> exact-token guest evidence retrieval
  -> CubeShim/Cubelet exact generation acceptance
  -> lossless metrics
  -> NolaneWorld one-scrape correlation
```

No exporter, parser, RPC transport, or compatibility OOM path may create or repair authority.

### Types/functions

Implement a private token type that accepts only canonical 64-lowercase-hex characters representing exactly 32 bytes.

Implement state:

- `Empty`
- `Bound(token)`
- `Poisoned`

Operations:

- bind same token twice: idempotent
- bind different token while Bound: Poisoned
- bind while Poisoned: stays Poisoned
- consume on main Start: returns the token exactly once and resets the slot only after capturing the consumed state for that Start
- exec Start never consumes the main realization token
- invalid token cannot become Bound

Use a private internal annotation key owned by CubeShim for Task Update ingestion. Do not log the token value.

### Task Update integration

In `TaskService::update`, inspect only the internal realization-token annotation before/alongside existing resource update behavior. The annotation is observational metadata for the next main Start and must not alter ordinary resource-update behavior. Conflicting updates poison evidence only.

### Main Start integration

In `TaskService::start`, only the empty `exec_id` path consumes the current token-slot state and passes the result to sandbox `start_container`. Exec processes do not consume or replace it.

### RED tests

- canonical token accepted
- uppercase/short/long/non-hex rejected
- same bind idempotent
- conflicting bind poisons
- poisoned state never yields token
- main Start consumes once
- exec Start does not consume
- token value is not emitted from public proof/metric-facing data structures

## Task 3 — Thread the exact token to guest StartContainer

### Files

- Modify: `CubeShim/protoc/protos/agent.proto`
- Modify: `CubeShim/shim/src/sandbox/sb.rs`
- Modify: `agent/src/rpc.rs`
- Modify: `agent/src/sandbox.rs`

### Contract

Extend `StartContainerRequest` additively with an internal `bytes realization_token` field. The field carries the exact 32 bytes, not hex, from CubeShim to the guest. Existing clients that omit it remain valid and simply receive no Wave 21 evidence.

`SandBox::start_container` receives the consumed slot outcome. For a valid Bound token it writes the 32 bytes into the guest Start request. Empty/Poisoned/invalid state sends no token and leaves workload Start behavior unchanged.

Guest `do_start_container` must execute the normal container start even when evidence initialization is unavailable. After the exact main process is successfully started, it asks the guest evidence store to begin that token's realization using a fresh guest boottime sample and exact main-process identity. Evidence initialization failure is logged without token value and returns normal Start success.

### RED tests

- valid token reaches StartContainer request exactly
- poisoned/empty slot sends no token
- token transport failure does not replace/duplicate compatibility OOM handling
- normal Start succeeds if evidence setup fails

## Task 4 — Guest victim primitive/store and realization finalization

### Files

- Add: `agent/src/guest_oom_victim.rs`
- Modify: `agent/src/main.rs` module registration as needed
- Modify: `agent/src/sandbox.rs`
- Modify: `agent/src/rpc.rs`

### Pure types first

Implement:

- fixed-size `RealizationToken([u8; 32])`
- `RawVictimEvent { tid, tgid, start_boottime_ns, event_boot_ns, cgroup_v2_id }`
- `GuestProcessIdentity { tgid, starttime_ticks }`
- `VictimClass::{Main, Member}`
- `VictimRecord`
- `FinalizedRealizationEvidence`
- bounded `GuestVictimStore`

### Required store invariants

- max 1024 raw events retained for max 10 minutes
- max 256 finalized realizations retained for max 10 minutes
- max 64 exact victims accepted per realization; 65th poisons the realization rather than truncating
- duplicate byte-identical event is idempotent
- conflicting event for the same exact event identity poisons the realization
- `loss_epoch` captured at realization begin and finalize; any change poisons the realization
- finalization is immutable and one-shot
- missing capability is unknown, never negative evidence

### Guest-local timing

Only accept victim events where:

`realization_started_boot_ns <= event_boot_ns <= outcome_observed_boot_ns`

The upper bound is captured in authoritative guest `WaitProcess` after the wait has observed/reaped the exact main process. Do not compare guest boottime to host wall clock.

### MAIN classification

A raw event becomes MAIN only if:

- event TGID equals exact runtime-owned main-process PID, and
- event start lifetime converts exactly to the same `/proc/<pid>/stat` field-22 identity captured for the main process, and
- guest boot identity for the realization still matches.

PID equality alone is insufficient.

### MEMBER classification

A raw event becomes MEMBER only if exact event-time cgroup-v2 identity equals the exact container cgroup-v2 kernel ID recorded for the realization. MEMBER never upgrades to MAIN.

### `/proc` identity

Use robust field-22 parsing that tolerates spaces and `)` in `comm`; use a stable A/B sandwich around required cgroup/boot observations to reject PID reuse. Exact uint64 arithmetic only.

### RED tests

- window lower/upper bound inclusive
- before/after event rejected
- main TID may differ from TGID
- exact TGID+lifetime -> MAIN
- same TGID different lifetime -> not MAIN
- exact cgroup ID -> MEMBER
- different/unknown cgroup -> not MEMBER
- MAIN takes exact lifetime authority; MEMBER never implies MAIN
- >64 victims poisons
- loss_epoch change poisons
- finalization immutable
- old token cannot retrieve newer realization
- boot-id mismatch poisons/unknown

## Task 5 — Guest `oom:mark_victim` collector

### Files

- Continue: `agent/src/guest_oom_victim.rs`
- Modify only dependency files proven necessary by the chosen existing Rust stack: `agent/Cargo.toml` and lockfile if required.

### Collector behavior

Implement a capability-gated positive-event collector for guest Linux `oom:mark_victim`. Prefer an existing repository-compatible eBPF/BTF mechanism; do not introduce a large unrelated runtime. The collector must capture victim identity at kernel event time, not reconstruct it later from PID alone.

Required event-time fields:

- victim TID
- victim TGID
- process lifetime primitive sufficient for exact `/proc` starttime bridge
- event `CLOCK_BOOTTIME` nanoseconds
- exact cgroup-v2 kernel identity when provable

Any ring-buffer loss increments a monotonically increasing `loss_epoch`. Attach/load/BTF/cgroup failures make Wave 21 unavailable but do not fail agent startup or containers.

### RED tests

Separate pure decoder/layout tests from privileged attach tests. Privileged live attach is capability-gated; pure contract tests must run on ordinary CI.
